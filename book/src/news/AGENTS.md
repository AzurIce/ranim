# book/src/news — 版本纪事（News）目录约定

本文件是 `book/src/news/` 的**目录级规则**，面向在此目录下撰写、修订版本
纪事的 AI agent 与人类贡献者。仓库级 PR 与贡献流程遵守仓库根目录的
`AGENTS.md`。

## 定位：类似 Bevy News 的版本纪事

- 本目录按版本收录**新特性纪事**（`v0.X/README.md`），体裁对标 Bevy 的
  release news：每个版本一篇长文，逐特性讲清楚**做了什么、为什么这么做**，
  配代码示例、mermaid 图与截图。
- 它**不是实现前的设计文档**：内容在特性落地后（或收敛过程中）撰写，
  而不是先于实现立项。目录名从 `designs/` 更名为 `news/` 正是为了让名字
  与实际的写作方式一致。
- 它也**不是 changelog**：fix、CI、devshell、依赖升级、文档修复等不进
  正文。入篇标准是"值得向用户与贡献者说明的事"——新特性、架构级变更、
  破坏性迁移。个别引入了面向用户接口变化的 fix（如渲染缓冲 API 签名
  变更）可以用一小节带过。

## 生命周期：发布前是草稿，发布即冻结

- **开发中版本的篇目是 living draft**：随 main 演进持续改写。某个设计被
  后续 PR 收敛时（例如求值协议在 #177 → #183 → #186 间的两次重写），
  直接把对应章节改写为收敛后的实现描述，不保留中间态的历史——中间态
  去看对应的 PR。
- **版本发布时冻结**：发布后不再回改该篇；此后的变更写进下一个版本的
  draft。
- 每篇开头标注状态与覆盖范围：

  ```markdown
  > **Status: Draft** — 随 main 更新，v0.X 发布时冻结。
  > 已覆盖：#A、#B。待补：#C、#D。
  ```

### 历史篇目的补写

为早已发布的版本事后补写纪事时，按该版本**发布时点**的快照描述，用对应
tag 的源码（`git show v0.X:<path>`）核实 API 断言，**不按当前实现回改**；
文首 Status 行标注补写与覆盖的 PR 范围：

  ```markdown
  > **Status: Backfilled（补写）** — 覆盖 #A–#B；按 v0.X 发布时点快照描述。
  ```

补写是首次发布而非回改，"发布即冻结"的语义不变。

## 每篇的结构约定

- **按主题分节**（一个特性或一次架构变更一节），不按 PR 逐条罗列；同一
  主题的多个 PR 在节内合并叙述，节首给出相关 PR 链接。正文中裸写的 `#N`
  引用由 `issue-links` 预处理器（`book/preprocessors/mdbook-issue-links/`）
  在构建时自动链接到 GitHub（issue 编号经 GitHub 重定向落到 `/issues/N`），
  无需手写链接；代码块、行内代码与 URL 内不生效。
- 破坏性变更加 `## BREAKING CHANGES` 小节，写清迁移路径，用 before/after
  代码块对照。
- **深度不降级**：news ≠ 摘要。动机与设计权衡（如"带宽贵于 ALU"、
  "placement lives in `Transformed` only" 这类原则）、语义边界、以及
  "为什么不是另一个方案"都要写透。
- 图片等资源放在对应版本目录下，用相对路径引用。
- 语言与 book 其余章节一致：正文用中文，代码与 API 名保持英文。

### 语体：进展展示，不是问题记录

News 是高信息密度的"展示/汇报"体（对标 Bevy News）：

- 每节以**能力与结果**开场——"ranim 现在能……""X 自此成立"；调试过程与
  问题史不进正文，"暴露了坑""修掉发散""曾因 X 而损坏"一类表述不出现；
- fix 只在用户可感知时以一句结果带过（如"MOV 输出自此稳定正确"），不展开
  来龙去脉；纯内部修复不入篇；
- 局限照实写，但作为**能力边界**表述，并尽量指出前路；
- 多引导读者动手："试试 `xxx` example"是标准收尾；
- 外部贡献者点名致谢。

### 图示、公式与表格的门槛

图示服务于"文字承载不了的结构"，不为装饰。添加前先过这个清单：

- **mermaid**：仅用于四类结构——时序/并发（`sequenceDiagram`）、空间/树状
  结构（flowchart）、架构演进对比（分 era 的 flowchart）、数据流/管线。
  同一概念在 `understand/` 已有同类图时**链接而不重画**。
- **typst 公式**（`$...$` / `$$...$$`，Typst 语法）：只写"正文断言本身"的
  公式（语义约定、算法核心，如逆转置法向、投影混合）；推导过程去
  `understand/`。
- **表格**：限 3×3 左右的短枚举——格式矩阵、性能对照、能力契约；更长的
  列表仍用条目。
- **图片**：只用真实产物——PR 存档截图或仓库内渲染产物；历史（补写）篇
  不配当代渲染图（时代错位，违背快照语义）。图片下载到与文章同级的
  `assets/` 目录、以描述性 kebab-case 命名，正文用相对路径引用，图注注明
  来源 PR。PR 正文里的 `user-attachments` 图片下载时需带浏览器
  User-Agent 并走 HTTP/1.1（HEAD 与默认 h2 会被 403/中断）；演示视频不收，
  优先收录 before/after 对比与 UI 演示。
- 图中的类型名、模块名必须与正文及源码一致，可对照对应 tag 源码核实。

## 与其他文档的分工

- **跨版本仍然成立的概念与用法**（求值协议、`Transformed` 模型的日常
  使用等）写入 `book/src/understand/` 对应章节；news 只负责"这个版本
  发生了什么、为什么"，不承担教程与 API 手册职责，需要时链接过去。
- news 章节里的 API 行为断言同样要求能在源码 rustdoc 中证实；book 可能
  滞后，源码是唯一事实来源。
